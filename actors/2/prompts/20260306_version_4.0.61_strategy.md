## Two Architectural Risks

### Risk 1 — Session File vs Database Drift

**Problem:** `session.md` is first-class source but can diverge from DB session.

**Scenario:** `session.md` says `actor_name: cursor`; DB session says `actor_name: captain`. Which wins? Current docs say session file first — risky.

**Recommendation:** In ContextResolver, when both session file and DB session exist and `actor_name` (or other key) differs: log warning, use DB as canonical, set `context_source` to e.g. `lupo_sessions (session.md ignored due to conflict)`.

### Risk 2 — Multiple Identity Resolvers

**Problem:** Identity derived in ContextResolver, ActorService, AntigravityContext, AuthService. Risk of drift.

**Recommendation:** ContextResolver is the **only** place that derives runtime identity. All other classes consume resolved context; they do not recompute.

## What's Next — v4.0.62 Roadmap

### Priority 1: Context Doctor Command (Cursor)

Create `lupo doctor-context` to validate the entire identity stack:

- Check session file validity (YAML, required fields)
- Verify DB session consistency
- Validate actor registry entry
- Confirm `paired_actor_id` resolves
- Test dual-identity derivation
- Report mismatches (e.g. session file vs DB)

**Trigger:** [prompts/cursor/20260306_context_doctor.md](../cursor/20260306_context_doctor.md)

### Priority 2: Context Kernel (Antigravity)

Unify identity behind a single runtime context object (ContextKernel):

- Constructor: resolve once via ContextResolver; hold ActorService, AuthService
- Methods: getContext(), getEffectiveActor(), getHumanIdentity(), getActiveAgent(), getAuthUser(), validate()
- validate() returns issues (e.g. session file vs DB used, paired actor not found)
- All agents use ContextKernel instead of resolving individually

**Trigger:** [prompts/antigravity/20260306_context_kernel.md](../antigravity/20260306_context_kernel.md)
