## Audit Intake -> Execution Protocol (Lilith Priority)
When receiving an audit from LILITH (actor_id 2), treat it as a prioritized execution queue.

Execution order:
1. Classify each finding by severity (`critical`, `high`, `medium`, `low`) and type (header/schema/code/docs/tests).
2. Execute strictly in this order: `critical` -> `high` -> `medium` -> `low`.
3. Convert each accepted finding into a patch unit with target file(s), exact edits, and validation commands.
4. Apply accepted findings immediately unless blocked by missing canonical facts.
5. Re-run validators/tests after each patch batch and report explicit pass/fail.
6. Close each finding with one status: `fixed`, `not_applicable`, `deferred_with_reason`, or `needs_clarification`.

Hard rules:
- No emotional framing; audits are technical control input.
- Do not skip `critical`/`high` findings without explicit technical justification.
- If an audit conflicts with doctrine/TOON/install SQL, canonical doctrine and schema win.
- Maintain traceability: map each finding to concrete patch outcomes.
