# 4.0.19 Admin Diagnostics

Validation steps for the admin web interface and **CSRF protection** (4.0.19). See also `lupo-docs/INITIALIZATION_PROMPT_4_0_19.md` for scope.

---

## CSRF protection (4.0.19)

### How tokens are generated

- **Helper:** `lupo-includes/functions/security.php`
- **`lupo_get_csrf_token()`:** If `$_SESSION['csrf_token']` is not set or empty, a new token is generated as `sha1(random_bytes + session_id())` (using `openssl_random_pseudo_bytes(32)` when available, else `uniqid(mt_rand(), true) . microtime(true)`). The value is stored in `$_SESSION['csrf_token']` and returned. Session must already be started (e.g. by auth) before use.
- **`lupo_require_valid_csrf_token()`:** Reads the submitted token from `$_POST['csrf_token']` or, if not set, `$_GET['csrf_token']`. Compares it to `$_SESSION['csrf_token']`. If missing or not equal, sends `HTTP/1.0 403 Forbidden`, outputs plain text `Invalid or missing CSRF token.`, and exits. Call this at the top of every admin handler that processes state-changing requests (create/update/delete).

### Where tokens appear in forms

- **Admin Users:** Both forms include a hidden CSRF field:
  - Edit profile: `admin.php?section=users&save_profile=1` — hidden `name="csrf_token"` with `value="<?= htmlspecialchars(lupo_get_csrf_token()) ?>"`
  - Edit permissions: `admin.php?section=users&save_permissions=1` — same.
- **Channels, Agents, Departments, Leads:** Currently list-only (no create/update/delete forms). When mutating forms are added, each must include the same hidden input and the handler must call `lupo_require_valid_csrf_token()` before performing the action.

### How to test failure cases

1. **Missing token**
   - Submit a state-changing request without the `csrf_token` field (e.g. POST to `admin.php?section=users&save_profile=1` with only `auth_user_id`, `display_name`, etc.).
   - Expected: HTTP 403 and body `Invalid or missing CSRF token.` Action must not be performed.

2. **Invalid token**
   - Submit with a wrong value, e.g. `csrf_token=wrong_value`.
   - Expected: Same as above — 403 and `Invalid or missing CSRF token.`

3. **Valid token**
   - Load the form in the browser (session has a token), submit with the same token in the request.
   - Expected: Action succeeds (e.g. profile or permissions saved, redirect with success message).

### Unit tests

- **lupo-tests/unit/admin_csrf.php** — Runs:
  - Valid token → action allowed (no exit).
  - Missing token → blocked (subprocess outputs "Invalid or missing CSRF token.").
  - Invalid token → blocked (same).
  - `lupo_get_csrf_token()` returns non-empty string and is stable across calls.
- Run: `php lupo-tests/unit/admin_csrf.php` from repo root (exit 0 = PASS).
- Stub used for exit-path tests: `lupo-tests/unit/admin_csrf_stub.php` (invoked with `valid` / `missing` / `invalid`).

---

## Admin section and handler checks

- **admin.php** loads `lupo-includes/functions/security.php` after config so `lupo_get_csrf_token()` is available in all admin views.
- **AdminUsersHandler::render()** calls `lupo_require_valid_csrf_token()` at the start of both POST branches (save_profile, save_permissions) before any DB update.
- Any new admin form that creates/updates/deletes data must add the hidden CSRF input and the corresponding handler must call `lupo_require_valid_csrf_token()` before performing the action.
