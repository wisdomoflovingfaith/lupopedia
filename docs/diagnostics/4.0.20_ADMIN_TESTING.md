# 4.0.20 Admin Testing and Diagnostics

Admin diagnostics (T2) provide **local-only, dev-only** JSON logging for permission checks, CSRF validation, session introspection, and admin actions. No feature or UI changes; diagnostics only.

---

## Overview

- **Location:** `logs/admin/` — one file per calendar day: `YYYY-MM-DD.jsonl` (e.g. `2026-02-19.jsonl`). Directory is created on first write.
- **Format:** JSON lines (one JSON object per line). Each entry includes `type` and `timestamp` (ISO 8601 via `gmdate('c')`).
- **Rotation:** When a day’s file exceeds **1MB**, it is renamed to `YYYY-MM-DD.jsonl.1` and a new `YYYY-MM-DD.jsonl` is started. Rotation uses **flock** (LOCK_EX) to avoid races.
- **Security:** Logs are local-only; never exposed publicly. `logs/` is in `.gitignore`.

---

## Log formats

### permission_check

Emitted when admin access is evaluated (after login, at top of admin.php).

```json
{"type":"permission_check","timestamp":"2026-02-19T18:00:00+00:00","actor_id":10000,"roles":["admin"],"resource":"admin","allowed":true}
```

- **actor_id:** Current actor ID (0 if unknown).
- **roles:** List of role keys (e.g. `["admin"]` when allowed, `[]` when denied).
- **resource:** Resource identifier (e.g. `"admin"`).
- **allowed:** Whether access was granted.

### csrf

Emitted inside `lupo_require_valid_csrf_token()` on every call (success or failure).

```json
{"type":"csrf","timestamp":"2026-02-19T18:00:00+00:00","actor_id":10000,"token_present":true,"token_valid":true}
```

- **token_present:** Whether a token was submitted (POST/GET).
- **token_valid:** Whether the token matched the session token.

### session

Emitted once per admin page load (after login, at top of admin.php).

```json
{"type":"session","timestamp":"2026-02-19T18:00:00+00:00","actor_id":10000,"session_age":3600,"ip":"127.0.0.1"}
```

- **session_age:** Seconds since session creation (0 if unknown).
- **ip:** Client IP (dev-only; sensitive).

### admin_action

Emitted after state-changing admin actions (e.g. save profile, save permissions).

```json
{"type":"admin_action","timestamp":"2026-02-19T18:00:00+00:00","actor_id":10000,"action":"save_profile","target_type":"auth_user","target_id":2001,"success":true}
```

- **action:** e.g. `save_profile`, `save_permissions`.
- **target_type:** e.g. `auth_user`, `actor_channel_role`.
- **target_id:** ID of the affected entity.
- **success:** Whether the action completed successfully.

---

## Rotation behavior

- **Threshold:** 1MB per day file.
- **Suffix:** Rotated file is renamed to `YYYY-MM-DD.jsonl.1`. Only one rotated file (`.1`) is kept per day.
- **Locking:** Before rename, the writer holds an exclusive flock on the file to prevent concurrent rotation/writes.

## Example shell queries

```bash
# View all permission denials
grep '"allowed":false' logs/admin/*.jsonl

# Find CSRF failures by actor (requires jq)
jq 'select(.type=="csrf" and .token_valid==false)' logs/admin/*.jsonl

# Count admin actions per day
grep -c '"type":"admin_action"' logs/admin/2026-02-19.jsonl
```

## How to test permission failures

1. Log in as a **non-admin** user (no captain/administrator on channel 1, no owner on admin module).
2. Open `http://localhost/lupopedia/admin.php`.
3. Expect: "Access denied" message in the main content area.
4. Check `logs/admin/YYYY-MM-DD.jsonl`: you should see:
   - `permission_check` with `"allowed":false` and `"roles":[]`.
   - `session` with that user’s `actor_id` and IP.

---

## How to test CSRF failures

1. **Missing token:** POST to `admin.php?section=users&save_profile=1` with no `csrf_token` field (e.g. with curl or a form without the hidden input).
   - Expect: HTTP 403 and body "Invalid or missing CSRF token."
   - Log: `csrf` with `token_present:false`, `token_valid:false`.

2. **Invalid token:** Same URL with `csrf_token=wrong_value`.
   - Expect: Same 403 and message.
   - Log: `csrf` with `token_present:true`, `token_valid:false`.

3. **Valid token:** Submit the real form from the browser (with a valid session and token).
   - Expect: Redirect and success message.
   - Log: `csrf` with `token_present:true`, `token_valid:true`.

---

## How to test session expiration

1. Log in, then expire the session (e.g. delete the session row in the DB or wait until expiry).
2. Request `admin.php` again.
3. Expect: Redirect to login (handled by auth, not by diagnostics).
4. Diagnostics run only **after** login; they do not run for unauthenticated requests. Session introspection appears only for authenticated admin page loads. To verify `session_age` in logs: log in, load admin, then inspect the `session` entry; `session_age` should increase on subsequent loads.

---

## How to test admin actions

1. Log in as an admin user.
2. **Save profile:** Go to Users → Edit profile for a user → change display name → Save.
   - Expect: Redirect and "Profile saved."
   - Log: `admin_action` with `action: "save_profile"`, `target_type: "auth_user"`, `target_id: <auth_user_id>`, `success: true` (or false if validation failed).

3. **Save permissions:** Go to Users → Edit permissions for a user → set channel 1 role → Save.
   - Expect: Redirect and "Permissions saved."
   - Log: `admin_action` with `action: "save_permissions"`, `target_type: "actor_channel_role"`, `target_id: <actor_id>`, `success: true`.

---

## Helper API

- **lupo-includes/functions/admin_diagnostics.php**
  - **lupo_diag_write($type, $data)** — Core writer; merges `type` and `timestamp` (ISO 8601) with `$data`, appends one JSON line. Rotates when file > 1MB (flock-based).
  - **lupo_diag_permission_check($actor_id, $role_list, $resource, $allowed)**
  - **lupo_diag_csrf($actor_id, $token_present, $token_valid)**
  - **lupo_diag_session($actor_id, $session_age, $ip)**
  - **lupo_diag_admin_action($actor_id, $action, $target_type, $target_id, $success)**

Integration points: permission and session in **admin.php**; CSRF in **lupo_require_valid_csrf_token()** (security.php); admin actions in **AdminUsersHandler** (save_profile, save_permissions).

## Regression suite (T3)

The regression suite defines the **baseline of correct behavior** before adversarial testing (T4). All tests are PHP 5.3-compatible and run from CLI; no admin behavior, routing, or schema is changed.

### Structure

- **tests/regression/admin/** — Admin UI: admin.php, sections (users, channels, agents, departments, leads), handlers, views, syntax.
- **tests/regression/auth/** — Auth helpers: require_login, current_user, require_admin, lupo_is_admin.
- **tests/regression/session/** — Session files and Session class; syntax and presence.
- **tests/regression/legacy/** — Legacy URLs (admin.php?section=...), handlers, content-controller; legacy_paths_runner.php runs the full legacy_paths regression.
- **tests/regression/csrf/** — CSRF: security.php, lupo_get_csrf_token, lupo_require_valid_csrf_token, admin_csrf_stub.
- **tests/regression/permissions/** — Permissions: lupo_is_admin, lupo_has_admin_for_channel, require_admin, AuthService.
- **tests/regression/installer/** — Installer/admin: admin entry, list handlers present; “Database not available” behavior when DB missing.

### How to run regression tests

From repo root:

```bash
sh scripts/run_regression_tests.sh
# or with path: sh scripts/run_regression_tests.sh /path/to/lupopedia
```

Or run all tests (unit, regression, integration, adversarial when present):

```bash
sh scripts/run_tests.sh
```

Individual scripts (from repo root):

```bash
php tests/regression/admin/admin_ui_regression.php
php tests/regression/auth/auth_regression.php
php tests/regression/session/session_regression.php
php tests/regression/csrf/csrf_regression.php
php tests/regression/permissions/permissions_regression.php
php tests/regression/legacy/legacy_admin_regression.php
php tests/regression/legacy/legacy_paths_runner.php
php tests/regression/installer/installer_admin_regression.php
```

### Expected output

- Each script exits **0** on success and prints one line ending with `PASS ...`.
- **run_regression_tests.sh** prints a summary: `PASS=n FAIL=n SKIP=n` and exits 0 only when FAIL=0.

### How to interpret failures

- **FAIL missing: path** — A required file is absent; add the file or fix the path.
- **FAIL syntax: path** — `php -l path` failed; fix PHP syntax.
- **FAIL ... not defined** — A required function or class is missing after require; fix the included file or the test’s defines/requires.
- If a regression fails after a change, the change may have broken the baseline; fix the code or update the test only if the new behavior is intended.

### Regression and adversarial testing (T4)

- **Regression** — Ensures existing behavior stays correct: files exist, syntax is valid, helpers and sections are present. It does not simulate attacks.
- **Adversarial (T4)** — Uses the regression baseline: if regression passes, adversarial tests then probe for correct *rejection* of bad input (missing/invalid CSRF, tampered session, privilege escalation, etc.). Run regression first; then run adversarial tests. A regression failure usually means the environment or codebase is broken; fix that before trusting adversarial results.

## Adversarial testing: harness (T4)

A **red-team test harness** runs HTTP-level attack vectors against the admin and auth stack. All tests are local-only, safe, and non-destructive (no schema or app logic changes).

### Purpose

- Verify the app **rejects** bad input with the right HTTP codes (e.g. 403 for missing/invalid CSRF, unauthorized access).
- Catch regressions (e.g. a change that allows requests without CSRF).
- Produce structured logs for audit.

### Attack vectors covered

| Vector | What is sent | Expected |
|--------|----------------|----------|
| csrf_missing | POST to admin save without `csrf_token` | 403 |
| csrf_invalid | POST with wrong `csrf_token` | 403 |
| unauthorized_access | GET admin.php with no session | 302 or 403 or 200 (login/deny) |
| privilege_escalation | Admin action with low-priv or no session | 403 |
| malformed_long_param | Very long cookie value | No 500 |
| sql_injection_probe | `' OR '1'='1` in query | No 500 (parameterized queries) |
| xss_probe | `<script>` in query | No 500; output escaped |
| session_tamper | Request with fake session cookie | 302 or 403 |
| rate_limit_test | Rapid repeated GETs | No 500 |

### How to run

From repo root (server must be running, e.g. `http://localhost/lupopedia`):

```bash
php tests/adversarial/run.php
# Or with base URL:
php tests/adversarial/run.php http://localhost/lupopedia
```

Or via the full test script:

```bash
sh scripts/run_tests.sh
# Adversarial section runs: sh scripts/run_adversarial_tests.sh REPO_ROOT [BASE_URL]
```

Sanity check (one vector: missing CSRF → 403):

```bash
php tests/adversarial/sanity_test.php [BASE_URL]
```

### How to interpret results

- **PASS** — The server returned the expected HTTP code (e.g. 403 for CSRF).
- **FAIL** — The server returned something else (e.g. 200 when 403 was expected). Investigate.
- If the server is not running, requests will fail (e.g. connection refused); vectors will show FAIL. Start the server and re-run.

### Expected pass/fail patterns

- **csrf_missing**, **csrf_invalid**: Should **PASS** (403) when CSRF protection is enabled.
- **unauthorized_access**: Should **PASS** (302 to login or 403).
- **privilege_escalation**: Should **PASS** (403) when using a low-priv session or no session.
- **session_tamper**: Should **PASS** (302 or 403) when the session is invalid.
- **malformed_long_param**, **sql_injection_probe**, **xss_probe**, **rate_limit_test**: Should **PASS** (no 500; app handles input safely).

Results are logged as JSON lines in `tests/adversarial/results/YYYY-MM-DD.jsonl`. See `tests/adversarial/README.md` for format and adding new vectors.
