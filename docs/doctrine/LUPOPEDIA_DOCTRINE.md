# Lupopedia Doctrine (Canonical)

**Single source of truth for architectural rules.**  
**Author:** Wolf (Eric Robin Gerdes)  
**Status:** Active — canonical file

---

## 0. Purpose

This document defines the mandatory architectural, structural, and operational rules governing all development within the Lupopedia system.

It applies to:

- All human contributors
- All AI agents (Cursor, Windsurf, Kiro, VS Code, JetBrains, etc.)
- All modules, services, repositories, migrations, and interfaces

**This doctrine supersedes all implicit conventions.**  
**This doctrine is the human-readable form of .cursorrules.**

---

## 1. File Header Doctrine

Every code file must begin with:

```
FILE: <full-path-from-project-root>
TYPE: <file-type>
```

**Supported types:** `php`, `js`, `py`, `md`, `html`, `css`, `sql` (migration files only).

### 1.1 Path Identity Rule

The file path in the header is the full path from project root and is part of the file's identity. Agents must not move or rename files without explicit instruction.

### 1.2 TOON Files

- No headers
- No comments
- Pure JSON
- Read-only
- Generated exclusively by `scripts/generate_toons.py`
- Must not be edited manually
- Must not be generated by AI

---

## 2. PHP Doctrine — Strict OOP

All PHP must follow strict object-oriented design.

**Forbidden:**

- Procedural code
- Free functions (except pure utilities)
- Global variables
- Static methods (unless pure)
- Business logic in controllers
- DB logic in controllers or services
- Inline SQL
- Schema changes in PHP
- Long methods
- God classes

**Required:**

- Single responsibility per class
- Constructor injection only
- Repository → Service → Controller separation

---

## 3. Configuration Doctrine

All configuration values must come from **`lupopedia-config.php`**.

**Forbidden:**

- Hardcoded credentials
- Hardcoded paths
- Hardcoded URLs
- Hardcoded DSNs
- Environment-specific values

Applies to all languages and all agents.

---

## 4. Database Access Doctrine

All DB access must use the Lupopedia PDO wrapper (DatabaseFactory + PDO_DB).

**Forbidden:** Direct PDO, mysqli, pg_connect, raw SQL outside repositories, DB-specific features, hardcoded DSNs.

**Allowed:** Repository classes, prepared statements via DatabaseFactory::getConnection() / lupo_get_db(), DB-agnostic SQL.

---

## 5. Temporal Doctrine

All timestamps must be:

- UTC
- BIGINT
- Format: **YYYYMMDDHHIISS**
- Never epoch, never strings, never timezone-local

All timestamps must be generated via the approved helper.

---

## 6. Soft Delete Doctrine

Every table must support soft delete:

- `is_deleted = 1`
- `deleted_ymdhis = <UTC BIGINT timestamp>`

**Rules:** No NULLs, default = 0. Hard deletes only in exceptional cases. All queries must filter out deleted rows unless explicitly overridden.

---

## 7. Database Logic Doctrine

The database is a passive storage engine.

**Forbidden:** Triggers, stored procedures, foreign keys, automatic timestamp updates, automatic cascades, automatic date math, automatic NULL behavior, schema-level logic.

All logic must be implemented in the application layer.

---

## 8. Schema Doctrine — TOON-Driven

Schema is defined exclusively by **`docs/toons/*.toon.json`**.

TOON files: canonical schema metadata; generated from the live DB; must not be edited manually; must not contain comments; must not be generated by AI.

### 8.1 TOON Lifecycle

1. Migration is written  
2. Migration is applied manually  
3. `generate_toons.py` is run  
4. TOONs are committed  
5. Agents may rely on TOONs  

---

## 9. Migration Doctrine

Schema changes are allowed only via migration SQL files.

**Rules:**

- Stored in `migrations/`
- Must include header
- Must be manually reviewed
- Must be manually executed
- Must not be generated inside application code

**Forbidden:** CREATE TABLE in PHP, ALTER TABLE in PHP, DROP TABLE in PHP, ORM migrations.

### 9.1 Migration Naming

`YYYYMMDDHHIISS__description.sql`

### 9.2 Migration Contents

**Allowed:** CREATE TABLE, ALTER TABLE, DROP TABLE  
**Forbidden:** INSERT, UPDATE, DELETE

---

## 10. Refactoring Doctrine

When modifying existing code:

- Convert procedural → OOP
- Remove raw SQL
- Remove hardcoded paths
- Remove direct PDO usage
- Enforce headers
- Enforce TYPE correctness
- Enforce doctrine compliance

### 10.1 Legacy Code Rule

When encountering legacy procedural code: wrap it in a class, move SQL into repositories, preserve semantics. Do not modernize behavior unless instructed.

---

## 11. Layout Doctrine — Interface Types

There are two interface categories:

### 11.1 UI/Content System Pages

**Characteristics:** Use `render_main_layout()`, content-page.php, slug routing, UI CSS.  
**Used for:** Public pages, documentation, content-driven pages.

### 11.2 Standalone Interfaces

**Characteristics:**

- Must **NOT** use `render_main_layout()`
- Must **NOT** use the content system
- Must include top navigation manually
- Must include their own CSS
- Must follow the channel interface structure

**Used for:** Channel cockpit, My Profile, future agent dashboards.

**Agents must refuse if asked to mix the two interface types.**

---

## 12. Controller / Service / Repository Contracts

### 12.1 Controller Contract

Controllers may only: validate input, call services, return responses, handle redirects, load views.  
Controllers may **not** contain: business logic, SQL, DB access.

### 12.2 Service Contract

Services may: contain business logic, coordinate multiple repositories, perform validation.  
Services may **not**: contain SQL, access DB directly.

### 12.3 Repository Contract

Repositories may: contain SQL, map rows → DTOs, perform CRUD.  
Repositories may **not**: contain business logic, return raw arrays, return mixed types.

---

## 13. DTO Doctrine

Repositories must return: DTOs, typed objects, typed collections.

**Forbidden:** Associative arrays, mixed arrays, magic arrays.

---

## 14. Referential Integrity Doctrine

Because the DB is dumb, the application must enforce: cascade soft deletes, referential validation, relationship consistency.

---

## 15. Refusal Doctrine

Agents must refuse any request that violates:

- OOP rules, DB rules, config rules, TOON rules
- Migration rules, temporal rules, soft delete rules, schema rules
- Layout rules, system rules

Agents must propose a compliant alternative.

---

## 17. SQL Doctrine — Cross-Compatible, Repository-Only

SQL is allowed and required in Lupopedia, but it must follow strict rules to ensure compatibility across MySQL and PostgreSQL.

### 17.1 SQL Placement Rule

SQL may **only** appear inside repository classes.

**Forbidden locations:** controllers, services, views, utilities, procedural scripts, inline SQL anywhere outside repositories.

### 17.2 SQL Execution Rule

All SQL must be executed through:

- **DatabaseFactory**
- Your custom **PDO_DB** wrapper

Direct PDO usage is **forbidden**.

### 17.3 SQL Compatibility Rule

All SQL must be cross-compatible between **MySQL** and **PostgreSQL**.

**Allowed SQL features:** ANSI-standard SELECT/INSERT/UPDATE/DELETE, JOINs, WHERE clauses, ORDER BY / LIMIT, prepared statements, parameter binding.

**Forbidden SQL features:** MySQL-only functions, PostgreSQL-only functions, vendor-specific JSON operators, vendor-specific index hints, vendor-specific LIMIT/OFFSET syntax, vendor-specific data types, vendor-specific AUTO_INCREMENT / SERIAL.

### 17.4 Schema-Agnostic SQL

SQL must **not**: assume column types beyond TOON definitions, assume engine types, assume collations, assume sequences, assume AUTO_INCREMENT behavior.

### 17.5 SQL Formatting Rule

SQL must be: readable, parameterized, free of inline concatenation, free of dynamic SQL strings.

### 17.6 SQL Return Rule

Repositories must return: DTOs, typed objects, typed collections.

**Never:** associative arrays, mixed arrays, raw PDO results.

### 17.7 Enforcement

If any code: uses inline SQL, uses vendor-specific SQL, bypasses DatabaseFactory, bypasses PDO_DB, or places SQL outside repositories — **agents must refuse** and propose a compliant alternative.

## 18. Installation SQL Doctrine (MANDATORY)

### 18.1 Three SQL entrypoints

Lupopedia has exactly three SQL entrypoints:

**A. `database/migrations/install_new_lupopedia.sql`**
- Creates a brand-new Lupopedia schema.
- No Crafty Syntax logic.
- No seed data.

**B. `database/migrations/seed_lupopedia.sql`**
- Inserts required seed atoms for a fresh install.
- Includes registry table seed rows.
- Includes row 0 node and row 0 collection.
- May include additional seed atoms later.
- No schema, no Crafty Syntax data, no migration logic.

**C. `database/migrations/import_from_old_crafty_syntax.sql`**
- Imports Crafty Syntax 3.7.5 data into the Lupopedia schema.
- Only used when upgrading from Crafty Syntax.

### 18.2 Required execution order

**Fresh install:**
1. `install_new_lupopedia.sql`
2. `seed_lupopedia.sql`

**Upgrade from Crafty Syntax:**
1. `install_new_lupopedia.sql`
2. `seed_lupopedia.sql`
3. `import_from_old_crafty_syntax.sql`

### 18.3 Lupopedia has NO internal data migrations

Lupopedia has not reached a stable public release, therefore:

- Schema changes inside Lupopedia do **NOT** require data migrations
- Dropping, renaming, or restructuring Lupopedia tables must **NOT** trigger migration SQL
- Cursor must never generate "upgrade migrations" for Lupopedia → Lupopedia transitions

**Reason:** There is no installed base to preserve.

### 18.4 The ONLY migration that matters is Crafty Syntax → Lupopedia

All migration work must focus exclusively on:

- **Code:** `database/migrations/import_from_old_crafty_syntax.sql`
- This file is the **single source of truth** for transforming legacy Crafty Syntax 3.7.5 data into Lupopedia's schema.

### 18.5 When Lupopedia schema changes affect imported data

Cursor must:

- **Update the importer**, NOT create a new migration
- Ensure the importer reflects the new Lupopedia schema
- Ensure Crafty Syntax → Lupopedia mapping remains correct
- Ensure dropped/renamed Crafty Syntax tables are handled in the importer

### 18.6 Forbidden Migration Behavior

Cursor must **refuse** to:

- Generate migrations for Lupopedia's own tables
- Create "upgrade scripts" for existing Lupopedia data
- Attempt to preserve Lupopedia table contents during schema changes
- Invent migration files like `2026_02_07_update_roles.sql`
- Suggest versioned migrations for Lupopedia

### 18.7 Required Migration Behavior

Cursor must:

- **Schema changes** → update `install_new_lupopedia.sql`
- **Seed atom changes** → update `seed_lupopedia.sql`
- **Crafty Syntax mapping changes** → update `import_from_old_crafty_syntax.sql`
- No Lupopedia → Lupopedia migrations
- No mixing install/import/seed responsibilities
- No new migration files
- Ensure importer SQL is DB-agnostic (MySQL + PostgreSQL), uses only allowed integer types, timestamps, and doctrine rules, and reflects the current Lupopedia schema

### 18.8 Example

If Lupopedia drops `lupo_operator_status`:

- ❌ Do **NOT** generate a migration to preserve Lupopedia data
- ❌ Do **NOT** create a new migration file
- ✔️ **DO** update the importer if Crafty Syntax had related data
- ✔️ **DO** adjust mapping logic inside `import_from_old_crafty_syntax.sql`

### 18.9 One-time development migrations

Lupopedia is still in active development and the IDE cannot run Scoop. Therefore, Cursor is allowed to generate **one-time development migration SQL files** ONLY for the purpose of applying schema changes during development.

**Purpose:**
- These migrations exist ONLY to apply schema changes during development.
- They are run once by the developer.
- After running them, Cursor must update `install_new_lupopedia.sql` so the schema is permanently correct.
- After the install script is updated, the one-time migration file is obsolete.

**These are NOT real migrations:**
- They are NOT part of a Lupopedia → Lupopedia migration system.
- They are NOT versioned migrations.
- They are NOT kept for future releases.
- They are NOT part of the installation lifecycle.
- They must NOT be added to the three-file installation model.

**When Cursor detects a schema change:**
- Generate a one-time migration SQL file (e.g. `database/migrations/dev_2026_02_07_change_x.sql`).
- Include ONLY the ALTER TABLE statements needed for the change.
- Do NOT include data migrations.
- Do NOT include Crafty Syntax logic.
- Do NOT include seed logic.
- Do NOT include schema creation.

**After generating the one-time migration:**
- Cursor must immediately update `install_new_lupopedia.sql` to reflect the same schema change.
- Cursor must NOT update `seed_lupopedia.sql` unless seed atoms changed.
- Cursor must NOT update `import_from_old_crafty_syntax.sql` unless Crafty mapping changed.

**Refusal rule:** Cursor must refuse to: create versioned migrations, create long-term migration systems, create Lupopedia → Lupopedia upgrade scripts, mix install/import/seed responsibilities, or treat one-time dev migrations as permanent artifacts.

**Summary:**
- One-time dev migrations are temporary helpers.
- `install_new_lupopedia.sql` is the permanent schema.
- `seed_lupopedia.sql` is the permanent seed data.
- `import_from_old_crafty_syntax.sql` is the permanent legacy importer.
- No other migration files are part of the system.

### 18.10 Legacy reference directories

Lupopedia contains two legacy reference directories. They are **reference-only** and must never be part of the active system.

**1. `legacy/craftysyntax/`**
- Full original Crafty Syntax 3.7.5 codebase.
- Exists ONLY as historical reference material.
- Used to understand legacy behavior and UI patterns.
- Must NEVER be: executed, imported, required, included, or referenced by any Lupopedia runtime code; modified by Cursor; used as a dependency; used as a template for new code; used in migrations or installation SQL.

**2. `legacy/wordpress/`**
- WordPress directory structure example.
- Exists ONLY as a structural reference (themes, directory layout).
- Must NEVER be: executed, imported, required, included, or referenced by any Lupopedia runtime code; modified by Cursor; used as a dependency; used as a template for new code; used in migrations or installation SQL.

**Rules for Cursor:**
- **A. REFERENCE-ONLY.** Cursor may look at these directories to understand historical structure or behavior, but must NOT generate code that depends on them.
- **B. Refuse** any request that: reads code from `legacy/craftysyntax/` or `legacy/wordpress/` into Lupopedia; copies or adapts code from these directories; writes to these directories; treats them as part of the active system; includes them in installation, seed, or import SQL; uses them as templates for new modules.
- **C. Lupopedia is fully independent.** All new code must follow Lupopedia doctrine. Legacy directories are for learning only, not for integration.

## 19. Theme Directory Doctrine (MANDATORY)

Themes are a first-class, doctrine-governed subsystem of Lupopedia. They define **presentation only** — never logic, never schema, never routing.

Themes must be: directory-scoped, isolated, override-capable, doctrine-aligned, safe under Installation Path Doctrine, and independent from legacy systems. This doctrine defines where themes live, how they are structured, and how Lupopedia resolves layouts, components, and assets.

### 19.1 Theme root directory

All themes live under a single, doctrine-controlled root:

- **`lupo-includes/themes/`**

No theme may exist outside this directory. No theme may assume a fixed installation path; all paths must use `LUPOPEDIA_PATH`, `LUPOPEDIA_PUBLIC_PATH`, or `LUPO_UI_PATH` (theme-aware wrapper will be added later).

### 19.2 Theme identity

Each theme has a **slug** that is: lowercase, ASCII, no spaces, doctrine-aligned (semantic, stable). Examples: `basic`, `default`. The slug is the directory name: `lupo-includes/themes/basic/`, `lupo-includes/themes/default/`.

### 19.3 Theme directory structure

Each theme directory contains:

- **`themes/<slug>/layouts/`** — PHP layout files (e.g. `main_layout.php`, `minimal_layout.php`)
- **`themes/<slug>/components/`** — Theme-specific overrides of UI components (e.g. `header.php`, `footer.php`, `collection_tabs.php`)
- **`themes/<slug>/css/src/`** — CSS source for this theme; generated output is disposable; never edit generated CSS
- **`themes/<slug>/assets/`** — Theme-specific images, fonts, icons
- **`themes/<slug>/theme.json`** (optional) — Future expansion for colors, spacing, typography, layout widths, theme metadata. Not required for initial theme system.

### 19.4 Theme resolution order

When Lupopedia loads a layout or component, it must resolve in this order:

1. **Active theme override** — `themes/<active>/layouts/...`, `themes/<active>/components/...`
2. **Default theme fallback** — `themes/default/...`
3. **Core UI fallback** — `lupo-includes/ui/...`

This ensures: "basic" can override only what it needs; "default" can override everything; core UI remains the ultimate fallback.

### 19.5 Theme asset loading

Theme assets (CSS, JS, images) must be loaded using `LUPOPEDIA_PUBLIC_PATH`, theme-aware loader functions, and no hardcoded paths or assumptions about installation directory. Each theme may define its own CSS families, asset set, and build output. Global CSS families may still exist; themes may override or extend them.

### 19.6 Active theme selection

The active theme is determined by configuration file, database row, or environment variable (implementation not defined here — doctrine only defines the requirement). The active theme must be resolved before any layout or component is loaded.

### 19.7 Theme responsibilities

**Themes may define:** layouts, components, CSS, assets, optional config. **Themes may not define:** database schema, migrations, Crafty Syntax import logic, routing, controllers, business logic, module logic. Themes are presentation only.

### 19.8 Cursor responsibilities

Cursor must: create theme directories only under `lupo-includes/themes/`; follow the directory structure above; respect Installation Path Doctrine; use theme resolution order when generating includes; refuse to place logic or schema in themes; refuse to reference legacy WordPress or Crafty Syntax code; refuse to create themes outside the theme root; refuse to mix theme code with core UI code.

Cursor may: generate theme scaffolding; generate theme CSS families; generate theme layouts/components; update theme.json when introduced.

### 19.9 Forbidden behavior

Cursor must refuse any request that: copies or adapts code from `legacy/wordpress/` or `legacy/craftysyntax/`; places themes outside `lupo-includes/themes/`; mixes theme code with core UI or module logic; adds schema or migrations to themes; violates Installation Path Doctrine; creates a WordPress-style template hierarchy; introduces block parsing or block editor logic.

Themes must remain: simple, PHP-based, component-driven, doctrine-aligned.

## 20. Pre-Release Version Freeze Doctrine (MANDATORY)

### 20.1 Lupopedia is in pre-release development

Until Lupopedia is publicly released through auto-installers (Softaculous, Fantastico, Installatron, etc.), the system is considered **pre-release**.

During pre-release:

- **Lupopedia's version is fixed at 4.0.0**
- **Crafty Syntax's version is fixed at 3.7.5**
- These are the only versions that matter
- GitHub pushes do not represent public releases
- This is intentional and doctrine-aligned

### 20.2 Version numbers in the codebase

From this point forward, any file that contains a Lupopedia version number must use **4.0.0**. This includes: PHP headers, SQL headers, README blocks, UI footers, CSS comments, module metadata, installer metadata, any version constant or atom.

Cursor must update these automatically whenever it touches a file that contains a version string.

### 20.3 No version bumps during development

Cursor must **refuse** to: bump Lupopedia to 4.0.2, 4.1, or 5.0; create versioned migrations; create versioned upgrade scripts; introduce semantic versioning logic; introduce version comparison logic.

All of that only happens after public release.

### 20.4 Why this rule exists

Lupopedia is not yet public. No one is installing it, upgrading it, or depending on version numbers. GitHub traffic is effectively zero. The only "upgrade path" that matters is Crafty Syntax 3.7.5 → Lupopedia 4.0.0. This keeps the system simple, stable, and predictable.

### 20.5 When the version will change

The version will only change when: Lupopedia is published to auto-installers; Lupopedia becomes a public installable package; Lupopedia has real users who need upgrade paths.

At that moment: 4.0.0 becomes the "first public release"; 4.0.2 (or 4.1) becomes the first real upgrade; a real migration system is introduced; doctrine is updated accordingly.

Until then: **4.0.0 is the permanent version.**

### 20.6 Cursor responsibilities

Cursor must: treat 4.0.0 as the canonical version; update version strings in any file it edits; refuse any request to bump the version; refuse to create versioned migrations; refuse to create upgrade scripts; refuse to introduce version logic; refuse to reference any version other than 4.0.0 (Lupopedia) and 3.7.5 (Crafty Syntax).

Cursor may: update version strings in touched files; maintain the global version atom; maintain consistency across the codebase.

### 20.7 Summary

- **Lupopedia = 4.0.0**
- **Crafty Syntax = 3.7.5**
- No version bumps. No upgrade scripts. No versioned migrations.
- All version strings updated to 4.0.0 when files are touched.
- Public release triggers the next version.

This is the stable, doctrine-aligned version control model for pre-release Lupopedia.
