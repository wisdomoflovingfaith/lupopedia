# FLP — Doctrine Boundaries

**Status:** Permanent. Documentation only.  
**Audience:** All AI agents (including Cursor), contributors, and system stewards.  
**Override:** These boundaries apply to all FLP-related work. No FLP implementation may violate them.

---

## 1. Prohibitions — Cursor must not propose or generate

In the context of the Federated Likeness Protocol (and in line with Lupopedia’s database logic prohibition doctrine), Cursor must **not** propose or generate:

- **Foreign keys** — No REFERENCES, no FK constraints between tables for FLP or council relationships.
- **Triggers** — No BEFORE/AFTER INSERT/UPDATE/DELETE triggers for FLP data.
- **Stored procedures** — No procedures that implement FLP logic in the database.
- **Stored functions** — No functions that compute FLP values in the database.
- **Views** — No views that compute or derive FLP aggregates or relationships.
- **Generated or computed columns** — No database-side derivation of FLP values.
- **Timestamp defaults or ON UPDATE clauses** — No DEFAULT CURRENT_TIMESTAMP, no ON UPDATE CURRENT_TIMESTAMP, or similar automation for FLP tables or columns.
- **Any database-side automation** — No scheduled events, no DB-level workflows, no automatic state transitions.

All relationships in the FLP are **soft references** (e.g. stored IDs or keys; resolution in application code). All timestamps are **BIGINT(14)** written by application code in **YYYYMMDDHHIISS** format.

---

## 2. Schema source of truth: TOONs only

All schema changes must **originate from TOON files** (`docs/toons/*.toon.json`). Cursor must not infer schema from the live database, from existing SQL, or from ad-hoc design. If a new table or column is ever required for the FLP, it must be defined in a TOON (per project governance) and then reflected in install SQL and migrations per the two-place rule. Cursor does not create or edit TOONs; TOONs are generated by the project’s TOON generation process.

---

## 3. No schema inference from live DB

Cursor must **not** infer schema from the live database. The only sources of truth for schema are TOON files and the canonical install/migration SQL that aligns with them. FLP documentation and implementation must not assume columns or tables that are not present in the TOONs.

---

## 4. Primary key and reference key doctrine

When any table is created or referenced in FLP context (or elsewhere under Lupopedia doctrine):

- **Primary key** — Must **never** be named `id`. The primary key must follow the pattern:
  - **`<singular_table_name>_id`**
  - Example: table `lupo_council_log` → primary key `council_log_id`.
- **Reference keys** — Must use the **exact same column name** as the primary key of the referenced table. No generic or ambiguous names such as `id`, `ref_id`, `parent_id`, or `table_id` unless the referenced table is literally named that.
- **Ambiguous names** — Forbidden for primary and reference keys in FLP and Lupopedia schema.

This aligns with the project’s PK and reference naming doctrine (`.cursor/rules/pk-reference-naming-doctrine.mdc`).

---

## 5. Summary

| Rule | Requirement |
|------|-------------|
| **No DB logic** | No FKs, triggers, procedures, functions, views, generated columns, or timestamp automation. |
| **Soft references** | All relationships are soft references; resolution in application code. |
| **Timestamps** | BIGINT(14) YYYYMMDDHHIISS, written by application code only. |
| **Schema from TOONs** | All schema changes originate from TOON files only. |
| **No live DB inference** | Do not infer schema from the live database. |
| **PK naming** | Primary key: `<singular_table_name>_id`; never `id`. |
| **Reference naming** | Reference keys match the referenced table’s PK name exactly. |
