# Lupopedia Doctrine (v1.1)

**Canonical Architecture & Development Rules**  
**Author:** Wolf (Eric Robin Gerdes)  
**Status:** Active Governance Artifact  
**Version:** 1.1

---

## 0. Purpose

This document defines the mandatory architectural, structural, and operational rules governing all development within the Lupopedia system.

It applies to:

- All human contributors
- All AI agents (Cursor, Windsurf, Kiro, VS Code, JetBrains, etc.)
- All modules, services, repositories, migrations, and interfaces

**This doctrine supersedes all implicit conventions.**  
**This doctrine is the human-readable form of .cursorrules.**

---

## 1. File Header Doctrine

Every code file must begin with:

```
FILE: <full-path-from-project-root>
TYPE: <file-type>
```

**Supported types:** `php`, `js`, `py`, `md`, `html`, `css`, `sql` (migration files only).

### 1.1 Path Identity Rule

The file path in the header is the full path from project root and is part of the file's identity. Agents must not move or rename files without explicit instruction.

### 1.2 TOON Files

- No headers
- No comments
- Pure JSON
- Read-only
- Generated exclusively by `scripts/generate_toons.py`
- Must not be edited manually
- Must not be generated by AI

---

## 2. PHP Doctrine — Strict OOP

All PHP must follow strict object-oriented design.

**Forbidden:**

- Procedural code
- Free functions (except pure utilities)
- Global variables
- Static methods (unless pure)
- Business logic in controllers
- DB logic in controllers or services
- Inline SQL
- Schema changes in PHP
- Long methods
- God classes

**Required:**

- Single responsibility per class
- Constructor injection only
- Repository → Service → Controller separation

---

## 3. Configuration Doctrine

All configuration values must come from **`lupopedia-config.php`**.

**Forbidden:**

- Hardcoded credentials
- Hardcoded paths
- Hardcoded URLs
- Hardcoded DSNs
- Environment-specific values

Applies to all languages and all agents.

---

## 4. Database Access Doctrine

All DB access must use the Lupopedia PDO wrapper.

**Forbidden:** Direct PDO, mysqli, pg_connect, raw SQL outside repositories, DB-specific features, hardcoded DSNs.

**Allowed:** Repository classes, prepared statements via wrapper, DB-agnostic SQL.

---

## 5. Temporal Doctrine

All timestamps must be:

- UTC
- BIGINT
- Format: **YYYYMMDDHHIISS**
- Never epoch, never strings, never timezone-local

All timestamps must be generated via the approved helper.

---

## 6. Soft Delete Doctrine

Every table must support soft delete:

- `is_deleted = 1`
- `deleted_ymdhis = <UTC BIGINT timestamp>`

**Rules:** No NULLs, default = 0. Hard deletes only in exceptional cases. All queries must filter out deleted rows unless explicitly overridden.

---

## 7. Database Logic Doctrine

The database is a passive storage engine.

**Forbidden:** Triggers, stored procedures, foreign keys, automatic timestamp updates, automatic cascades, automatic date math, automatic NULL behavior, schema-level logic.

All logic must be implemented in the application layer.

---

## 8. Schema Doctrine — TOON-Driven

Schema is defined exclusively by **`docs/toons/*.toon.json`**.

TOON files: canonical schema metadata; generated from the live DB; must not be edited manually; must not contain comments; must not be generated by AI.

### 8.1 TOON Lifecycle

1. Migration is written  
2. Migration is applied manually  
3. `generate_toons.py` is run  
4. TOONs are committed  
5. Agents may rely on TOONs  

---

## 9. Migration Doctrine

Schema changes are allowed only via migration SQL files.

**Rules:**

- Stored in `migrations/`
- Must include header
- Must be manually reviewed
- Must be manually executed
- Must not be generated inside application code

**Forbidden:** CREATE TABLE in PHP, ALTER TABLE in PHP, DROP TABLE in PHP, ORM migrations.

### 9.1 Migration Naming

`YYYYMMDDHHIISS__description.sql`

### 9.2 Migration Contents

**Allowed:** CREATE TABLE, ALTER TABLE, DROP TABLE  
**Forbidden:** INSERT, UPDATE, DELETE

---

## 10. Refactoring Doctrine

When modifying existing code:

- Convert procedural → OOP
- Remove raw SQL
- Remove hardcoded paths
- Remove direct PDO usage
- Enforce headers
- Enforce TYPE correctness
- Enforce doctrine compliance

### 10.1 Legacy Code Rule

When encountering legacy procedural code: wrap it in a class, move SQL into repositories, preserve semantics. Do not modernize behavior unless instructed.

---

## 11. Layout Doctrine — Interface Types

There are two interface categories:

### 11.1 UI/Content System Pages

**Characteristics:** Use `render_main_layout()`, content-page.php, slug routing, UI CSS.  
**Used for:** Public pages, documentation, content-driven pages.

### 11.2 Standalone Interfaces

**Characteristics:**

- Must **NOT** use `render_main_layout()`
- Must **NOT** use the content system
- Must include top navigation manually
- Must include their own CSS
- Must follow the channel interface structure

**Used for:** Channel cockpit, My Profile, future agent dashboards.

**Agents must refuse if asked to mix the two interface types.**

---

## 12. Controller / Service / Repository Contracts

### 12.1 Controller Contract

Controllers may only: validate input, call services, return responses, handle redirects, load views.  
Controllers may **not** contain: business logic, SQL, DB access.

### 12.2 Service Contract

Services may: contain business logic, coordinate multiple repositories, perform validation.  
Services may **not**: contain SQL, access DB directly.

### 12.3 Repository Contract

Repositories may: contain SQL, map rows → DTOs, perform CRUD.  
Repositories may **not**: contain business logic, return raw arrays, return mixed types.

---

## 13. DTO Doctrine

Repositories must return: DTOs, typed objects, typed collections.

**Forbidden:** Associative arrays, mixed arrays, magic arrays.

---

## 14. Referential Integrity Doctrine

Because the DB is dumb, the application must enforce: cascade soft deletes, referential validation, relationship consistency.

---

## 15. Refusal Doctrine

Agents must refuse any request that violates:

- OOP rules, DB rules, config rules, TOON rules
- Migration rules, temporal rules, soft delete rules, schema rules
- Layout rules, system rules

Agents must propose a compliant alternative.

---

## 17. SQL Doctrine — Cross-Compatible, Repository-Only

SQL is allowed and required in Lupopedia, but it must follow strict rules to ensure compatibility across MySQL and PostgreSQL.

### 17.1 SQL Placement Rule

SQL may **only** appear inside repository classes.

**Forbidden locations:** controllers, services, views, utilities, procedural scripts, inline SQL anywhere outside repositories.

### 17.2 SQL Execution Rule

All SQL must be executed through:

- **DatabaseFactory**
- Your custom **PDO_DB** wrapper

Direct PDO usage is **forbidden**.

### 17.3 SQL Compatibility Rule

All SQL must be cross-compatible between **MySQL** and **PostgreSQL**.

**Allowed SQL features:** ANSI-standard SELECT/INSERT/UPDATE/DELETE, JOINs, WHERE clauses, ORDER BY / LIMIT, prepared statements, parameter binding.

**Forbidden SQL features:** MySQL-only functions, PostgreSQL-only functions, vendor-specific JSON operators, vendor-specific index hints, vendor-specific LIMIT/OFFSET syntax, vendor-specific data types, vendor-specific AUTO_INCREMENT / SERIAL.

### 17.4 Schema-Agnostic SQL

SQL must **not**: assume column types beyond TOON definitions, assume engine types, assume collations, assume sequences, assume AUTO_INCREMENT behavior.

### 17.5 SQL Formatting Rule

SQL must be: readable, parameterized, free of inline concatenation, free of dynamic SQL strings.

### 17.6 SQL Return Rule

Repositories must return: DTOs, typed objects, typed collections.

**Never:** associative arrays, mixed arrays, raw PDO results.

### 17.7 Enforcement

If any code: uses inline SQL, uses vendor-specific SQL, bypasses DatabaseFactory, bypasses PDO_DB, or places SQL outside repositories — **agents must refuse** and propose a compliant alternative.
