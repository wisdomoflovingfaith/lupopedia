# Translation Model Doctrine

## 1. Purpose
Lupopedia contains deeply technical continuity layers, resilient systems, and multi-agent coordination architectures that are true and tested, but confusing to external audiences. This translation doctrine ensures technical truth is preserved while providing an intentional explanation interface for executives, users, and external contributors. We never dilute truth into falsehood; we simply layer the explanation.

## 2. Layered Explanation System
All translations must follow a strict depth hierarchy. Always start at Layer 1 and only drop to Layer 3 when invited.

* **Layer 1 (The Outcome / The Why)**: What the system achieves, why it matters, and how it protects the user or business.
* **Layer 2 (The Conceptual Model)**: How the pieces interact conceptually without mentioning exact file paths, raw variables, or internal graph physics.
* **Layer 3 (Implementation Mechanics)**: The raw, unvarnished technical reality. Pathing, DB schemas, specific script logic.

## 3. Truth Preservation
Do not convert technical truth into vague fluff.
Every simplified explanation must remain faithful to the real implementation. We do not invent marketing nonsense. Clarity beats completeness in Layer 1.

## 4. Defined Audiences
Translations should pivot their phrasing based on the requested audience:
* **Executive**: Needs risk mitigation, business value, and systemic stability guarantees.
* **Non-Technical User**: Needs guidance on how to safely interact with the UI without breaking flows.
* **Support Operator**: Needs diagnostic cues and an understanding of what state the system is currently in.
* **Contributor / Developer**: Needs to understand how their isolated part hooks into the architectural reality without needing to read the entire 150-page doctrine first.
* **Auditor**: Needs the exact constitutional reality (Layer 3).

## 5. Historical Precedent
This approach isn't theoretical. Look to the Honolulu DMV system built in 1999—a solo dev project that successfully utilized CSV schemas and filesystem content out of a DB failure context. This precedent serves as proof that "continuity patterns" are battle-tested and resilient, not just "outdated text files". Keep this precedent in mind; we are building systems that survive.
