## Executive Summary

The work is largely solid. DB-first writer is well-structured, string_utils.py is correct, Session UA normalization is simple and clean, v3 header format is a genuine improvement. However there is **one blocking architectural conflict** that will cause silent failures unless addressed: two incompatible memory filesystem layouts now coexist, and `MemoryGraph.php` only understands one of them.

## What Cursor Did Well

### `db_memory_writer.py` — solid
- Idempotency via `content_hash + owner_actor_id + memory_key + memory_type` is correct
- `_generate_pk()` using 14-digit timestamp prefix + 4-digit sequence bucket is clean
- Symbolic ref resolution (`FILE:`, `CHANNEL:`, `TASK:`, `PRD-N`, bare key) handles the main cases

- `preg_replace('/[^A-Za-z0-9]/', '', $ua)` strips everything, lowercase, truncate 200

### BLOCKER 1: Two incompatible memory path conventions — `MemoryGraph.php` only knows one

**The conflict:**

| Created by | Path format | Example |
|------------|-------------|---------|
| Claude Code (this session) | `memory/{YYYY}/{MM}/M-{slug}-{date}.toon` | `memory/2026/04/M-constitutional-20260409.toon` |
| Cursor (v3 migration) | `memory/{channel_key}/{trust_tier}/{year}/{MM}/{slug}.toon` | `memory/constitutional/seed/prd-00-constitutional.toon` |
| Cursor (canonical transform) | `memory/{channel_key}/canonical/{YYYY-1000}/{MM}/{slug}.toon` | `memory/memory/canonical/1026/04/38-memory-unification.toon` |

Both layouts exist on disk right now. Verified:
- `memory/2026/04/M-constitutional-20260409.toon` ✓ (Claude Code)
- `memory/constitutional/seed/prd-00-constitutional.toon` ✓ (Cursor)
- `memory/memory/canonical/1026/04/` directory ✓ (Cursor, year = 2026-1000)

**`MemoryGraph.php` `findLatestToon()` behavior:**
- Scans `memory/{date('Y')}/{date('m')}/` = `memory/2026/04/`
- Finds Claude Code's files only
- Will never find Cursor's files because:
  - `constitutional/seed/` is not under a year directory
  - `memory/canonical/1026/04/` has year `1026`, not `2026`

**Current `active_memory_ref` in session.json:**
```
"active_memory_ref": "memory/2026/04/M-constitutional-20260409.toon"
```
This points to Claude Code's old format toon. The v3 PRD-00 `memory_key` is:
```
memory/constitutional/seed/prd-00-constitutional.toon
```
These are different files representing the same document. Neither references the other.

**Impact:** Any agent calling `php bin/memory.php load-context` gets the old Claude Code toon, not the v3 Cursor toons. The v3 memory is silently unreachable.

**Fix needed:** Either:
1. Update `MemoryGraph.php` to scan both path conventions (add `memory/{channel_key}/{tier}/` search), OR
2. Decide on one canonical path format and migrate

My recommendation: consolidate on Cursor's v3 path (it has semantic meaning), and update `findLatestToon()` to scan all subdirectories under `memory/` recursively. The current date-based scan was never robust enough anyway. This is a small change.

### BLOCKER 2: Session backward compatibility — existing sessions will be invalidated by `normalizeUserAgent`

**The issue:** `normalizeUserAgent()` is now called unconditionally in `extractFingerprint()`. Any session created before this change stored `ua_hash` computed from the raw UA string. After this change, the hash is computed from the normalized UA. The stored hash and the computed hash will never match.

**Effect:** Every existing session will fail its `ua_hash` validation check. All users get logged out on next request.

Cursor says "preserved backward compatibility" in the changelog. Reading `Session.php` line 804:
```php
$expected_ua_hash = hash('sha256', (string) $fp['user_agent'] . '|' . self::sessionSalt());
```
`$fp['user_agent']` IS the normalized value now (from `extractFingerprint()`), so the comparison is self-consistent — the hash is computed and validated both using normalized UA. Fine for new sessions. But stored `ua_hash` rows from before this change hold the old raw-UA hash value, and there's no migration.

**Severity depends on current install state.** If there are no active sessions (fresh dev install), this is fine. If there are real users, they get invalidated. Worth a note in the changelog: "all existing sessions invalidated — intentional for dev, needs migration script for production upgrade."

### MEDIUM 1: `DBMemoryWriter` fallback returns `0` as node ID — poisons compacted transcripts

When DB is unavailable, `_write_toon_file_fallback()` returns `0`.

In `migrate_transcript_to_memory.py`:
```python
node_id = writer.create_memory_node(toon, ...)
if compact:
    stub = compact_entry(entry, str(node_id), creation_ts)
```

With DB down: every entry gets `"memory_id": "0"` in the compacted transcript. That's not a memory ID, it's noise. If you later run `migrate_transcript_to_memory.py` again, these entries are skipped (they have `action=compacted` and a `memory_id`), but the ID is useless.

**Fix:** When fallback is active, use the toon file path or the toon `id` field as the `memory_id` stub, not `0`. Example: `"memory_id": "fs:M-development-prd_files_44-20260409001808"`.

### MEDIUM 2: `generate_json_headers.py` will produce empty companions for v3-migrated PRDs

The 12 Cursor-migrated PRDs now have minimal v3 YAML frontmatter. Fields like `purpose`, `status`, `tags`, and `outbound_edges` are gone from YAML — they've been moved to the toon sidecar.

`generate_json_headers.py` reads `lupopedia.headers` and `lupopedia.edges` from the YAML. For the 12 migrated PRDs, it will find only `channel_key`, `trust_tier`, and `memory_key` — the companion JSON will be nearly empty.

**Fix needed:** When `generate_json_headers.py` encounters a v3 header, it should:
1. Read the `memory_key` field
2. Load the referenced toon sidecar
3. Extract `edges`, `tags`, `purpose` from the toon sidecar to populate the companion

This is a small but important update to keep the two systems in sync.

---

### MEDIUM 3: `MemoryGraph.php` `resolveRef()` won't resolve `memory_key` v3 paths that use canonical year (1026)

The canonical year transform subtracts 1000 from the actual year. `memory/memory/canonical/1026/04/` is a real directory.

`MemoryGraph.php` `findLatestToon()` scans:
- `memory/2026/04/` ← exists, has Claude Code toons
- Falls back to `memory/2026/` ← exists
- Falls back to `memory/` ← exists

Year `1026` is `< 2000`, so it's under `memory/1026/` from a flat layout perspective — but in the new layout it's `memory/{channel_key}/canonical/1026/04/`. The recursive scan in `findToonById()` WILL find them because it walks the whole tree. But `findLatestToon()` won't prioritize them.

When `active_memory_ref` is null and Cursor's v3 toons are the only ones present, an agent will get no context.
