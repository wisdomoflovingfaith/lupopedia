# Semantic Monitoring Architecture

**Version**: 4.0.88  
**Author**: CASCADE (actor_id 105)

## 1. Executive Summary

The Semantic Monitoring Architecture transforms Lupopedia from a simple live chat system into a comprehensive visitor intelligence platform. It captures, processes, and analyzes visitor behavior across monitored domains while maintaining full compatibility with Crafty Syntax 3.7.5 features.

**Key Innovation**: Uses the existing `livehelp_js.php` → `image.php` data flow to build a semantic knowledge graph without requiring client-side changes.

## 2. System Components

### 2.1 Data Collection Layer

#### JavaScript Widget (livehelp_js.php)
- **Role**: Client-side data collection and UI generation
- **Generated by**: PHP at request time
- **Data Captured**: Page URL, title, referrer, engagement interactions
- **Backward Compatibility**: Maintains all Crafty Syntax behaviors

#### Data Receiver (image.php)
- **Role**: Server-side data processing and storage
- **Enhanced**: Added semantic processing pipeline
- **Processing Flow**: Sanitization → Content Registration → Visit Recording → Edge Creation

### 2.2 Storage Layer

#### Core Semantic Tables
- `lupo_contents` - Auto-registered page entities
- `lupo_visits` - Individual visit records with session tracking
- `lupo_edges` - Navigation graph (page-to-page transitions)
- `lupo_semantic_content_views` - Aggregated view statistics

#### Engagement Tables (NEW)
- `lupo_engagement_signals` - Likes, shares, ratings, bookmarks
- `lupo_comments` - Threaded comment system
- `lupo_hashtags` - Hashtag registry and usage tracking
- `lupo_content_tags` - Content-to-hashtag relationships
- `lupo_user_bookmarks` - User-specific content saves

### 2.3 Integration Layer

#### ROSE — Voice Channeling Agent (Actor 3)

**Purpose**: ROSE reads artifacts from an agent and writes packets **as that agent** (same speaker).

**Process**:
1. ROSE scans `channels/*/broadcasts/`, `threads/`, `directives/` 
2. ROSE identifies artifacts from a specific agent (e.g., LILITH)
3. ROSE analyzes content for insights
4. ROSE writes a packet with:
   - **SPEAKER = that agent** (the agent whose artifacts were read)
   - TARGET = @recipient
   - message = insight
   - mood_RGB = hex color

**Key Rule**: ROSE **never** writes `speaker: rose`. ROSE channels the voice of the agent it is interpreting.

**Why Only ROSE Has `mood_RGB`**:
- Emotional context is ROSE's exclusive domain
- Other agents do not generate `mood_RGB`

**What ROSE Does NOT Do**:
- Speak as itself (`speaker: rose`)
- Modify original artifacts

**Example**:
When Cascade writes a broadcast about PRD completion, ROSE may add:
- `mood_vector: "4B0082"` (indigo — reflective, insightful)
- Additional insights about what the PRD might have missed

#### Channel-Based History
- **Role**: Decision and communication history
- **Storage**: `channels/42/` artifacts
- **Format**: Structured markdown with LUPOPEDIA headers
- **Access**: Queryable through channel API

## 3. Data Flow Architecture

### 3.1 Data Flow with ROSE

1. Agent (Cascade, Windsurf, etc.) writes artifact to `channels/42/` (broadcasts, threads, directives)
2. **ROSE scans** for new artifacts
3. **ROSE analyzes** for additional insights
4. **ROSE creates enhanced version** with:
   - Same `actor_name` as original
   - Added `mood_vector` field
   - New insights appended
5. Enhanced artifact written to same channel location
6. Original artifact preserved (no deletion)

### 3.2 Visitor Journey Tracking

```
1. Visitor lands on page → livehelp_js.php generates widget
2. Widget captures page data → image.php receives ping
3. image.php processes:
   a. Auto-registers page in lupo_contents
   b. Records visit in lupo_visits
   c. Creates navigation edge in lupo_edges
   d. Updates view counts in lupo_semantic_content_views
4. Engagement interactions → engagement tables
5. ROSE interprets patterns → channel artifacts
```

### 3.2 Federation Node Scoping

All data is scoped by `federation_node_id`:
- **Default**: Node 1 (single installation)
- **Multi-site**: Each site gets its own node
- **Data Isolation**: Queries always filter by node
- **Cross-node**: Aggregation through federation APIs

### 3.3 Real-time vs Batch Processing

#### Real-time (image.php)
- Page registration (must be immediate)
- Visit recording (must be immediate)
- Navigation edge creation (must be immediate)
- Engagement signal processing (must be immediate)

#### Batch (cron/scheduled)
- View count aggregation
- Engagement analytics calculation
- Trending content detection
- Performance optimization

### 5.2 Database Design Principles (MANDATORY)
All database design MUST follow the rules in `rules/root/`:

#### No Foreign Keys Doctrine (database-logic-prohibition-doctrine.md)
- **NO FOREIGN KEY constraints** - All relationships enforced in application code
- **NO REFERENCES clauses** - Manual referential integrity
- **NO TRIGGER definitions** - All logic in PHP code
- **NO stored procedures/functions** - Application-side logic only
- **NO DEFAULT CURRENT_TIMESTAMP** - Explicit timestamps in PHP

#### Primary Key Naming Doctrine (pk-reference-naming-doctrine.md)
- **Primary keys**: `<singular_table_name>_id` format
- **NEVER use `id`** - Always explicit naming
- **Reference keys**: Use exact same name as referenced PK
- **Examples**: `actor_id`, `content_id`, `visit_id` (not `id`)

#### Timestamp Doctrine (timestamp-doctrine.md)
- **Format**: BIGINT `YYYYMMDDHHIISS` (UTC)
- **Set in PHP**: `gmdate('YmdHis')`
- **No database automation** - All timestamps explicit
- **Timezone**: Always UTC

### 5.3 Polymorphic Design Patterns

Lupopedia uses sophisticated polymorphic patterns:

#### Generic Relationship Tables
- `lupo_edges` - Handles ANY entity relationships:
  - Navigation: content → content transitions
  - Actor relationships: actor ↔ content ↔ actor
  - Decision relationships: decision ↔ evidence ↔ influences
  - Context relationships: context ↔ entity ↔ context

#### Type-Based Discrimination
- `entity_type` columns determine row type
- `relation_type` columns define relationship nature
- `edge_type` and `edge_category` for navigation classification

#### JSON Metadata Storage
- `properties_json` columns for extensible data
- `metadata_json` columns for configuration
- Avoids schema changes for new attributes

### 5.4 Federation & Multi-Node Architecture

#### Federation Node Scoping
- ALL tables have `federation_node_id` where applicable
- Data isolation per installation
- Cross-node aggregation through federation APIs
- Node-specific configurations via `lupo_federation_nodes`

#### Channel-Based Organization
- `channel_id` scopes data to specific channels
- Channel 42 for protocol development
- Channel-based artifact storage instead of status files
- Multi-channel actor assignments via `lupo_actor_channel_roles`

### 6.3 Crafty Syntax Session Tracking (RESEARCH REQUIRED)

Based on analysis of `gc.php` and `archivefootsteps()` function, Crafty Syntax uses:

#### Session-Based Tracking Pattern
1. **Real-time Tracking**: `livehelp_visit_track` records each page view as it happens
2. **Session End Processing**: When session expires (5 minutes inactivity), `archivefootsteps()` processes:
   - Extracts unique pages visited
   - Creates navigation paths (entry → exit transitions)
   - Updates daily/monthly aggregates
   - Records first-time vs repeat visits

#### Key Tables to Understand
- `livehelp_visit_track` - Real-time page tracking
- `livehelp_visits_daily/monthly` - Aggregated visit counts
- `livehelp_paths_firsts/monthly` - Navigation path analysis
- `livehelp_referers_daily/monthly` - Referrer tracking

#### Implementation Strategy
Lupopedia 4.0.88 must:
1. **Study `archivefootsteps()`** - Understand path creation logic
2. **Replicate session processing** - Move from real-time to session-end aggregation
3. **Map to new schema** - Convert to existing `lupo_visits`, `lupo_edges`, `lupo_analytics_paths`
4. **Preserve analytics** - Maintain daily/monthly reporting capabilities
5. **Handle complexity** - gc.php shows sophisticated session processing

#### Key Insights from gc.php Analysis
- **Session timeout handling** - 5 minutes inactivity triggers session end
- **Path deduplication** - `$arrayofurls` prevents duplicate page counting
- **Navigation graph creation** - `livehelp_paths_firsts/monthly` for first-time paths
- **Recursive deletion** - Complex tree structure for old data cleanup
- **Random cleanup** - Probabilistic cleanup to prevent performance impact
- **Department attribution** - `firstdepartment` tracked throughout session
- **Referrer tracking** - `camefrom` preserved for session attribution

**CRITICAL**: This is NOT simple garbage collection - it's sophisticated visitor intelligence processing.
