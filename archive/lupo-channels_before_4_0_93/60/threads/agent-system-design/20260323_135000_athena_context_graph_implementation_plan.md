# ATHENA — Context Graph Implementation Plan (Version 4.0.86)

## 1. System Overview

The Context Graph provides a lightweight, edge-based representation of Lupopedia's workspaces:

- Channels are top-level context containers.
- Threads are scoped work units inside a channel.
- Edges encode relationships (e.g., belongs_to, references, triggers, produces).
- All edge data lives in the canonical DB (`lupo_context_edges` table).
- No foreign keys, triggers, or auto-increment columns are used; every mutation passes through the service layer to guarantee determinism and auditability.

The plan below details the concrete steps required to materialize the finalized model (see `lupo-channels/61/threads/channel-definition/20260323_133000_wolfie_context_graph_final_resolution.md`) into a production-ready subsystem.

## 2. Database Implementation

| Item | Specification | Rationale |
|------|---------------|-----------|
| Table | `lupo_context_edges` (created under `LUPO_TABLE_PREFIX`) | Holds every edge record. |
| Columns | `edge_id BIGINT` (primary key, generated by `EdgeIdService` - deterministic, not `AUTO_INCREMENT`)<br>`source_type VARCHAR(64)` (e.g., `channel`, `thread`, `actor`)<br>`source_id BIGINT` (ID of the source entity)<br>`target_type VARCHAR(64)`<br>`target_id BIGINT`<br>`edge_type VARCHAR(64)` (e.g., `references`, `belongs_to`)<br>`metadata_json JSON` (optional free-form data)<br>`created_ymdhis BIGINT` (UTC timestamp)<br>`updated_ymdhis BIGINT`<br>`is_deleted TINYINT DEFAULT 0`<br>`deleted_ymdhis BIGINT DEFAULT 0` | All columns conform to the DB-canonical rules (BIGINT timestamps, soft-delete). |
| Primary Key | `edge_id` (unique) | Deterministic ID generation guarantees repeatable ordering. |
| Indexes | `idx_source` on (`source_type`, `source_id`)<br>`idx_target` on (`target_type`, `target_id`)<br>`idx_type` on (`edge_type`) | Enforced by the `EdgeService`; required for fast traversal. |
| Migration Script | `lupo-database/lupopedia/mysql/migrations/dev_20260323_001_create_lupo_context_edges.sql` (adds table, indexes, comments) | Must be run before any service code is deployed. |
| No FK / Triggers | The table contains no foreign-key constraints or database triggers; all integrity is enforced in the service layer. | Aligns with Lupopedia doctrine. |

## 3. Service Layer Design

All edge operations are performed through `EdgeService` (application-layer only). Each method is deterministic, logs to the forensic audit log, and respects the soft-delete policy.

| Method | Signature (PHP 5.3) | Behaviour |
|--------|----------------------|-----------|
| `createEdge($sourceType, $sourceId, $targetType, $targetId, $edgeType, $metadata = null)` | Returns `edge_id` (BIGINT). Throws on validation failure. | Calls `EdgeValidationService::validateCreate()`; generates deterministic `edge_id` via `EdgeIdService::nextId($sourceId, $targetId, $edgeType)`; inserts row inside a single transaction (no direct PDO usage). |
| `getEdges($filter = array())` | Returns array of edge records. | Accepts filter keys: `source_type`, `source_id`, `target_type`, `target_id`, `edge_type`; uses prepared statements; respects `is_deleted = 0`. |
| `deleteEdge($edgeId)` | Returns bool. | Performs soft delete (`is_deleted = 1`, `deleted_ymdhis = gmdate('YmdHis')`); calls `EdgeConcurrencyService::acquireLock($edgeId)` before update. |
| `bulkUpsert(array $edges)` | Returns array of created/updated `edge_ids`. | Used for import/export sync; each edge passes through validation and concurrency services. |

All service classes reside under `app/Services/ContextGraph/` and use `DatabaseFactory::getConnection()` for DB access.

## 4. Validation Layer

`EdgeValidationService` guarantees that every edge respects the model's invariants before any write.

| Validation Rule | Description |
|-----------------|-------------|
| Schema Validation | Verify all required fields are present, types match (BIGINT for IDs, VARCHAR for types). |
| Scope Matrix | Enforce allowed `source_type` ↔ `target_type` pairs (e.g., `channel -> thread` allowed, `thread -> channel` prohibited). |
| Duplicate Detection | Reject creation if an identical edge (`source_type`, `source_id`, `target_type`, `target_id`, `edge_type`) already exists and is not soft-deleted. |
| Cycle Detection | Run a depth-first search limited to 5 hops to ensure no cycles are introduced for edge types that must remain acyclic (e.g., `belongs_to`). |
| Metadata Constraints | If `metadata_json` is supplied, ensure it is valid JSON and does not exceed 4 KB. |
| Timestamp Rules | `created_ymdhis` and `updated_ymdhis` must be set to `gmdate('YmdHis')` at insertion; updates must preserve immutability of `created_ymdhis`. |

All validation failures are logged to `lupo_audit_log` with `event_type = 'edge_validation_error'` and returned as a `400 Bad Request` to the caller.

## 5. Concurrency Model

`EdgeConcurrencyService` serializes edge mutations to avoid race conditions.

| Mechanism | Details |
|-----------|---------|
| Named Lock | `GET_LOCK('edge_mutation_<sourceId>_<targetId>', 5)` - ensures only one mutation affecting the same source/target pair runs at a time. |
| Retry Policy | On lock failure, retry up to 3 times with exponential back-off (500 ms, 1 s, 2 s). After the third failure, abort and log `event_type = 'edge_concurrency_failure'`. |
| Conflict Resolution | If two concurrent `createEdge` calls attempt the same edge, the service applies last-writer-wins based on `updated_ymdhis`. The earlier transaction is rolled back. |
| Isolation | All mutations execute in a single DB transaction; reads (`getEdges`) are allowed concurrently (`READ COMMITTED`). |

## 6. Resolution Engine

The `ResolutionEngine` is used by higher-level components (e.g., channel routing, thread discovery) to compute deterministic traversals.

| Function | Purpose |
|----------|---------|
| `resolveConflicts(array $edges)` | Given a set of candidate edges (e.g., from import), apply precedence rules: `belongs_to > references > produces`; timestamp order; newer edges win when types are equal. |
| `traverse($startId, $startType, $maxDepth = 10)` | Deterministically walks the graph, always expanding edges in lexicographic order of `edge_type` then `target_id`. Guarantees repeatable results for the same start node. |
| `getContextPath($channelId)` | Returns the ordered list of threads and actors reachable from a channel, using the deterministic traversal algorithm. |

All functions are pure (no side-effects) and return immutable data structures.

## 7. API Design

All external interactions with the edge system go through the REST API under `lupo-includes/modules/api/context_graph_api.php`.

| Endpoint | Method | Access | Payload / Response |
|----------|--------|--------|--------------------|
| `/api/context/edge` | `POST` | Authenticated agents with `write_edge` capability | JSON body matching `createEdge` signature. Returns `{ "edge_id": <bigint> }`. |
| `/api/context/edges` | `GET` | Authenticated agents with `read_edge` capability | Query parameters for filters (`source_type`, `source_id`, ...). Returns array of edge objects (excluding soft-deleted). |
| `/api/context/edge/{edge_id}` | `DELETE` | Authenticated agents with `write_edge` capability | Performs soft delete; returns `{ "deleted": true }`. |
| `/api/context/traverse` | `GET` | Authenticated agents with `read_edge` capability | Params: `start_type`, `start_id`, `max_depth`. Returns deterministic traversal list. |

Constraints enforced in the API layer:

- Read-only vs mutation boundaries: only the `POST`/`DELETE` endpoints mutate; `GET` endpoints are pure reads.
- No direct DB exposure: the API never returns raw DB rows; it always passes through the service layer.
- Deterministic responses: ordering of returned edge arrays is guaranteed by the service's sorting logic.
